1. Project overview
Monitor Portals is a desktop utility that removes inaccessible mouse-cursor boundaries between monitors with different dimensions, resolutions, scaling factors, or arrangements.

Instead of changing monitor resolutions or physically rearranging displays, the application creates configurable virtual connections between monitor edges.
Primary problem
Your current arrangement has a curved ultrawide external monitor (Monitor 2) above a smaller laptop display (Monitor 1).

The mouse can cross between them only where their rectangular display boundaries overlap. The remaining portions of the ultrawide monitor's bottom edge are blocked.
Project goals
1. Edge equalization: Make the full facing edges of differently sized monitors navigable.
2. Surround mode: Allow one monitor to be virtually accessible through all four edges of another.
3. Custom navigation: Let users define connections between specific monitor edges.
4. Automatic configuration: Detect monitor connection, disconnection, arrangement, resolution, and scaling changes.
5. Graphical configuration: Provide a simple interface for selecting monitors, modes, and navigation behavior.

4. Core algorithm design
This is the central technical part of the project.
A. Represent monitor geometry
Store each monitor's geometry using logical desktop coordinates.
const monitors = [
  {
    id: "external",
    x: 0,
    y: 0,
    width: 3440,
    height: 1440
  },
  {
    id: "laptop",
    x: 760,
    y: 1440,
    width: 1920,
    height: 1080
  }
];


These are example values. The actual values will be read from your GNOME configuration.

Use half-open rectangles:
\[
[x,x+W)\times[y,y+H)
\]

This avoids ambiguity about ownership of the last pixel.
B. Detect inaccessible boundaries
For your two-monitor case, calculate the horizontal overlap between the bottom of Monitor 2 and the top of Monitor 1.
\[
L=\max(x_1,x_2)
\]

\[
R=\min(x_1+W_1,x_2+W_2)
\]

If \(L < R\), the overlap is the interval \([L,R)\).

For the example layout, the ultrawide monitor has:
- Left blocked interval: \(0\)–\(760\)
- Normal crossing interval: \(760\)–\(2680\)
- Right blocked interval: \(2680\)–\(3440\)
The first prototype should detect these regions automatically.
C. Calculate the destination coordinates
For an edge mapped proportionally onto another edge, normalize the pointer's position.
\[
t=\operatorname{clamp}\left(\frac{x_s-x_{s,\min}}{W_s-1},0,1\right)
\]

Then map to the destination:
\[
x_d=x_{d,\min}+t(W_d-1)
\]

Finally, move the pointer a few logical pixels inside the destination to prevent repeated triggering.

The same algorithm works for vertical edges by replacing horizontal coordinates and widths with vertical coordinates and heights.
D. Define two different equalization policies
This is an important product decision.

Blocked-edge rescue — default MVP

Preserve normal cursor movement through existing shared boundaries. Redirect only attempts to cross blocked sections.

This is less disruptive and easier to implement reliably.



Full-edge proportional mapping — advanced

Apply proportional mapping to the entire designated edge, including areas that would normally cross directly.

This requires intercepting or controlling native crossings before the cursor enters the other display. Treat this as a separate technical investigation, not a guaranteed MVP feature.



E. Cursor transition algorithm
The initial engine can follow this logic:
ON POINTER MOTION:

  Read current pointer position and button state

  If feature is disabled:
      EXIT

  If a mouse button is held:
      EXIT

  Find the current monitor

  Determine whether pointer reached
  a configured exit boundary

  If no exit boundary:
      Reset transition state
      EXIT

  If the cursor is already transitioning:
      EXIT

  Find the destination monitor and entry edge

  If no valid route exists:
      EXIT

  Calculate destination position

  Apply inset and coordinate clamping

  Execute safe pointer relocation

  Verify the destination when possible

  Disarm transition until cursor moves
  away from the destination edge


Important: A pointer at an edge does not always mean the user intends to cross it. Later versions should distinguish outward movement from simply touching or sliding along the boundary. This may involve direction tracking, pointer-barrier events, or an optional short edge delay.
F. Configuration model
Each monitor connection should be represented as a directed rule.

For example:
{
  "schemaVersion": 1,
  "mode": "edge-equalizer",
  "routes": [
    {
      "source": {
        "monitor": "external",
        "edge": "bottom"
      },
      "destination": {
        "monitor": "laptop",
        "edge": "top"
      },
      "activation": "blocked-only",
      "mapping": "proportional",
      "enabled": true
    }
  ],
  "safety": {
    "disableDuringDrag": true,
    "landingInset": 3,
    "cooldownMs": 120
  }
}


Here, external and laptop are internal identifiers, not actual hardware connector names. The cooldown and inset values are initial design parameters to test, not confirmed optimal settings.

Representing mappings as directed rules also allows asymmetric behavior. For example, Monitor 2's bottom edge can use proportional mapping while Monitor 1's top edge uses a normal crossing.

7. Technical challenges and solutions
These deserve particular attention because they can determine whether the project works reliably.
Challenge	Proposed approach	Priority
Blocked cursor edges	Detect per-monitor boundaries rather than only global desktop edges	Critical
Pointer barriers	Route pointer movement through known valid monitor seams when necessary	Critical
Accidental jumping	Activation rules, small destination inset, disarm/rearm logic	Critical
Dragging windows	Suppress transitions while a mouse button is held	Critical
Overlapping native crossings	Preserve native movement in the MVP; investigate interception for full equalization	High
Different resolutions/scales	Use logical coordinates; normalize edge position	High
Monitor unplugged	Invalidate routes, refresh geometry, suspend affected mappings	High
Several destination monitors	Directed route graph with explicit priority and ambiguity handling	Medium
Pointer-confined applications	Respect compositor confinement, fail without repeated retries	High
Performance overhead	Event-driven checks with at most one processing pass per frame	High

One particularly important discovery: Mutter applies pointer barriers even to pointer warps. Cursor Wrap handles GNOME Shell barriers by moving across monitor seams in steps rather than always teleporting directly from source to destination. Its implementation provides a valuable technical reference for your pointer transport module. 
GitHub


It also demonstrates a safe approach that checks pointer motion at most once per frame and avoids continuous Wayland polling. 
GitHub


The extension must handle failures safely. For example, if the compositor refuses a warp during a game, the navigation engine should avoid repeatedly attempting the same transition.

8. Testing strategy
You should have two complementary test systems.

Unit tests: Verify geometry calculations, coordinate mapping, and route selection using synthetic monitor arrangements.

GNOME integration tests: Run the extension with real Mutter input handling, ideally in a nested or headless GNOME session, then verify that the resulting cursor coordinates match expectations.

The Cursor Wrap project already includes headless integration tests using virtual monitors and a virtual mouse. This is an excellent model for your future automated testing system.

Development workflow
The workflow should be:
1. Implement one small feature.
2. Run unit tests and linting.
3. Load the extension in a controlled GNOME environment.
4. Test the behavior.
5. Inspect shell logs.
6. Commit the working change to Git.
On Wayland, GNOME Shell generally cannot be restarted in place using the old X11 restart shortcut. Prefer a nested development session and log out/in when required to reload production-session changes.

The GNOME development documentation gives this command for a nested session on current GNOME versions:
dbus-run-session gnome-shell --devkit --wayland


Use the nested environment for early experiments, especially before implementing cursor movement in your everyday desktop.
